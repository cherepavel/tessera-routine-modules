# Status Evaluation

`StatusEvaluationWorkflowRoutine` версии **1.0.0** вычисляет статус исходной числовой
метрики по настраиваемым условиям. Функция `EvaluateStatus` возвращает обычную метрику:
`"0"` — OK, `"1"` — warning, `"2"` — alarm. Результат совместим с существующим
`ProcessStatus` и экспортом метрик; менять движок и Storage API не требуется.

## Аргументы EvaluateStatus

| Аргумент | Назначение |
| --- | --- |
| `DataId` | Обязательный ID одной метрики в local workspace; перед вызовом прочитать её через `GET ... AS ...`. |
| `MetricName` | Имя результата; по умолчанию идентификатор `RETURN` в нижнем регистре. |
| `WarningThreshold` | Числовой порог warning; необязателен, если задан alarm. |
| `WarningOperator` | Сравнение с порогом warning; по умолчанию `>=`. |
| `AlarmThreshold` | Числовой порог alarm; необязателен, если задан warning. |
| `AlarmOperator` | Сравнение с порогом alarm; по умолчанию `>=`. |
| `PromLabel_*` | Метки результата; дополняют метки исходной метрики, совпадающие ключи заменяются. |

Поддерживаются `>`, `>=`, `<`, `<=`, `==`, `!=`. Значения и пороги сравниваются через
`BigDecimal`, без округления до `double`; `10.0` и `10.00` равны. Числа задаются с
десятичной точкой, допускается экспоненциальная запись. Хотя бы один порог обязателен.
Оператор без соответствующего порога, пустой порог и повтор одного из перечисленных
обычных аргументов считаются ошибкой настройки.

Сначала проверяется alarm, затем warning. Если оба условия выполнены, результат — alarm;
если ни одно — OK. Пороги не обязаны возрастать: например, `<` позволяет описать слишком
низкое давление. Пересечения условий допустимы и разрешаются приоритетом alarm.
Логические выражения `AND/OR` в этой версии не поддерживаются.

Пример: `WarningThreshold=70`, `AlarmThreshold=90`, операторы по умолчанию:

| Значение T | Статус |
| --- | --- |
| `T < 70` | `0` |
| `70 <= T < 90` | `1` |
| `T >= 90` | `2` |

Для warning/alarm создаётся метка `reason` с путём ноды, именем исходной метрики,
входным `DataId`, фактическим значением, уровнем и сработавшим условием. Например:

```text
root.SourceA => temperature [DataId=RAW]=90 matches ALARM condition >= 90
```

Для OK метка `reason` отсутствует. Старая причина исходной метрики и `PromLabel_reason`
удаляются: этот ключ принадлежит вычислению статуса. Остальные метки сохраняются.
Исходная метрика не изменяется; результат получает время текущего вычисления.

## Ошибочные данные

Отсутствующий `DataId`, отсутствующая метрика, нечисловое значение, `NaN`, бесконечность
и ошибочная конфигурация завершают выполнение ошибкой, переводят рутину в `FATAL`
и не создают новый статус для этого вызова. В OK такие ситуации не преобразуются.
Локальный workspace очищается после каждого выполнения, включая ошибочное.

## Полная цепочка

Для двух дочерних нод `SourceA`, `SourceB` и родительской ноды:

1. В stage 1 каждой дочерней ноды выполнить [generate.mcg3dsl](examples/generate.mcg3dsl)
   через `DataGeneratorWorkflowRoutine` **1.1.0**. Это исходные значения температуры
   из диапазона `[0, 120)`. Для воспроизводимости можно задать `Seed` в routine ENV.
2. В stage 2 каждой дочерней ноды выполнить [evaluate.mcg3dsl](examples/evaluate.mcg3dsl)
   через `StatusEvaluationWorkflowRoutine` **1.0.0**. Storage `MEASUREMENTS` должен
   быть доступен обоим stage, итоговый `STATUS` — родительской ноде.
3. После выполнения дочерних нод выполнить в родительской ноде
   [aggregate.mcg3dsl](examples/aggregate.mcg3dsl) через существующий
   `ProcessingStatusWorkflowRoutine`. Он выберет максимальную тяжесть и объединит причины.

Каждый файл подключается стандартным параметром `MCg3-WorkflowRoutine-DSL-File`;
также поддерживается inline-параметр `MCg3-WorkflowRoutine-DSL`.
В Configurator используйте автоматически назначенные storage ID вместо имён из примера.
Метаданные `EvaluateStatus` публикуют существующие виджеты `FuncENV`, `FuncInputData`,
`FuncOutputData` через Project IO SPI; дополнительные виджеты не нужны.

## Сборка и проверки

```sh
mvn -pl workflowroutine-status-evaluation -am verify
```

Артефакт: `target/workflowroutine-status-evaluation-1.0.0-shaded.jar`.
При запуске необходим `sharedresources-project-common-1.0.0-shaded.jar` в shared-модулях.
Генератор и агрегатор нужны для полной цепочки, но не являются runtime-зависимостями
этой рутины.

Проверки включают все операторы и точные границы, ошибочные данные и настройки,
работу с файлами DSL и Global Storage, чтение metadata собранного JAR. Отдельная JVM
с `--limit-modules java.se` загружает фабрики через `ServiceLoader` из shaded JAR,
генерирует значения `69`, `70`, `90`, вычисляет `0/1/2` и проверяет агрегацию вместе
с сохранением причин. Проверки статусов не зависят от случайного попадания в диапазон.
